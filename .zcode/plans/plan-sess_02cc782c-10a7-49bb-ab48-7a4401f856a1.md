# Databases — full Notion-style build-out

## Scope (from your decisions)
Everything except automations/templates/inline-blocks/sub-items:
- **Views** (Database vs View model) + **filters** + **sorts** + view switcher; add **List, Board, Gallery** views on top of the existing Table.
- **Row-as-page** + row/col **lifecycle** (delete row, delete column, reorder rows & columns).
- **More property types**: `multi_select` (with colors), `status`, and system types (`created_time`, `created_by`, `last_edited_time`, `last_edited_by`).
- **Relation** (two-way link between databases) + **Rollup** (aggregate through a relation).
- Databases **stay page-level** (rendered below the editor) — no inline-block refactor.

The build is sequenced as **7 vertical slices**; each ends with passing tests before the next starts. Slices 1–2 are foundational (everything else depends on them); 3–6 are largely independent; 7 is the capstone (relation+rollup, which depends on slice 6's type framework).

A new spec dir `specs/014-databases-v2/` will hold the full plan/spec/tasks; the existing `012`/`013` specs are left as-is (history).

## Slice 1 — Schema migration + shared types (foundation)

Everything downstream depends on the data model.

### `backend/prisma/schema.prisma`
- Extend `PropertyType` enum: add `multi_select`, `status`, `relation`, `rollup`, `created_time`, `created_by`, `last_edited_time`, `last_edited_by`. (Existing: `text/number/select/date/checkbox/url/formula`.)
- New **`DatabaseView`** model:
  ```
  model DatabaseView {
    id           String   @id @default(cuid())
    database_id  String
    name         String   @default("Table")
    type         ViewType            // enum: table | list | board | gallery
    config       Json                // { filters: Filter[], sorts: Sort[], group_by?: string, hidden?: string[] }
    order        Int      @default(0)
    created_at   DateTime @default(now())
    database     Database @relation(fields: [database_id], references: [id], onDelete: Cascade)
    @@index([database_id])
    @@map("database_views")
  }
  ```
- New `ViewType` enum: `table | list | board | gallery`.
- `Property` model: add `relation_database_id String?` (the target db for `relation` props) and `rollup_config Json?` (`{ relation_property_id, target_property_id, aggregation }`). Add relation to `Database` for `relation_database_id`.
- **Backfill on migrate**: every existing `Database` gets one default `DatabaseView` `{ name: "Table", type: "table", config: {} }`, so the model is never view-less. Implemented as a raw-SQL migration step (Prisma can't seed in migrations) — `INSERT INTO database_views ...` for each row in `databases`.
- Migration: `prisma migrate dev --name databases_v2`.

### `shared/api-types.ts`
- Extend `PropertyType` with the new union members.
- Add `ViewType = "table" | "list" | "board" | "gallery"`.
- Add `Filter` / `Sort` interfaces and a `ViewConfig`:
  ```
  export interface Filter {
    property: string;          // property name
    op: "eq" | "ne" | "contains" | "gt" | "gte" | "lt" | "lte" | "is_empty" | "is_not_empty" | "any_of" | "none_of";
    value?: string | number | boolean | string[] | null;
  }
  export interface Sort { property: string; direction: "asc" | "desc"; }
  export interface ViewConfig { filters: Filter[]; sorts: Sort[]; group_by?: string | null; hidden?: string[]; }
  export interface DatabaseViewDTO { id; database_id; name; type: ViewType; config: ViewConfig; order: number; }
  ```
- Extend `PropertyDTO` with optional `relation_database_id?` and `rollup_config?`.
- Extend `DatabaseDTO` with `views: DatabaseViewDTO[]`.
- Add `MoveProperty`/`ReorderProperty` request types and `MoveRow` request types (for slice 2).
- Add `RelationValue` (`{ page_id }`) and `RollupValue` (a scalar) doc comments.
- Rebuild `shared/dist`.

### `shared/contracts.md`
- Add a `## Databases v2` section documenting every new endpoint (listed in the slices below), mirroring the existing format.

**Verify (slice 1):** `prisma migrate dev` succeeds; `yarn typecheck` clean (frontend will show unused-type warnings only, no errors since nothing consumes them yet).

## Slice 2 — Row & column lifecycle + reorder (backend)

Foundational CRUD the UI has been missing. New endpoints:

- `DELETE /databases/:databaseId/properties/:propertyId` — delete a column (cascade its `PropertyValue`s). `minAccess: EDITOR`. Reject if it's the last property (keep ≥1).
- `POST /databases/:databaseId/properties/:propertyId/move` — reorder a column. Body `{ before_id? | after_id? }`. Recompute `order` for all sibling properties (re-pack to integers 0..n) in a transaction. Mirrors the block reorder anchor pattern.
- `DELETE /rows/:rowPageId` — delete a row (soft-delete the backing Page: `is_deleted=true`; excluded from `getDatabase` which already filters `is_deleted:false`). `minAccess: EDITOR`.
- `POST /databases/:databaseId/rows/:rowPageId/move` — reorder a row. Body `{ before_id? | after_id? }`. Store order: add an `order Float @default(0)` to the `Page` row representation for database rows — **decision: store row order on `PropertyValue`? No.** Add `row_order Float` column to `database_rows`... but rows ARE pages, there's no join table. Cleanest: add `order Float? ` to `Page` used only when `database_id` is set, OR a lightweight `DatabaseRowOrder` join table `(database_id, page_id, order)`. **Chosen: add `row_order Float @default(0)` to `Page`** (nullable semantics: null = created_at ordering for non-row pages; row pages set it on add). `getDatabase` orders by `row_order asc, created_at asc`. Reorder uses fractional-index `computeOrder` from `blocks/order.ts` (already battle-tested).

### Backend changes
- `databases.schema.ts`: add `moveSchema = z.object({ before_id: z.string().optional(), after_id: z.string().optional() })`.
- `databases.service.ts`: `deleteProperty`, `moveProperty`, `deleteRow`, `moveRow`. `addRow` sets `row_order` to max+1.
- `databases.controller.ts` + `databases.routes.ts`: wire the 4 endpoints.
- `getDatabase`: change `orderBy` to `[{ row_order: "asc" }, { created_at: "asc" }]`.

**Verify (slice 2):** new e2e tests: delete column (property + its values gone), move column (order changes), delete row (gone from db), reorder row (order changes). Existing sheets tests still green.

## Slice 3 — Views + filters + sorts (backend + frontend)

The Notion-defining slice: one data source, many lenses.

### Backend
- **Views CRUD**:
  - `POST /databases/:databaseId/views` — create a view `{ name, type, config? }`. First view defaults to `{type:"table"}`. (Migration backfill guarantees ≥1 exists, but creation lets users add Board/List/Gallery.)
  - `PATCH /databases/:databaseId/views/:viewId` — update name/type/config.
  - `DELETE /databases/:databaseId/views/:viewId` — delete (reject if it's the last view).
  - `POST /databases/:databaseId/views/:viewId/move` — reorder view tabs.
- **Filter/sort application in `getDatabase`**: add optional `?view_id=` query param. When present, load that view's `config`, then apply filters + sorts **in the service layer** (Postgres-side `where` for value filters where feasible, in-memory for formula/rollup). `DatabaseDTO.rows` becomes the *view-filtered, sorted* set; `properties` gains a `hidden` consideration (frontend hides them). For table view with no view_id, behavior is unchanged (backward compat).
  - Filter semantics per type: text→`contains`; number/date→`eq/ne/gt/gte/lt/lte`; select/status→`eq/ne/any_of/none_of`; checkbox→`eq`; multi_select→`any_of/none_of/contains`; all types→`is_empty/is_not_empty`.
  - Sort: stable multi-key, applied after filter. Formula/rollup sorts done in-memory (value already computed).
- New `databases.service.ts` functions: `createView`, `updateView`, `deleteView`, `moveView`, and a `applyViewConfig(rows, properties, config)` pure helper (testable in isolation).

### Frontend
- New `shared` `ViewConfig` consumed by a new `useDatabaseView` state (which view is active — local state, persisted via `PATCH /views/:id` on change).
- **View switcher tabs** above the grid: each view is a tab; `+` adds a view (modal: name + type). Active tab highlighted; drag-to-reorder tabs (native HTML5, mirroring the PageTree DnD from the previous task).
- **Filter UI**: a "Filter" button opens a row of condition builders (property dropdown + op dropdown + value input, type-aware). `AND` logic between conditions. Edits PATCH the view's config (debounced).
- **Sort UI**: a "Sort" button → add sorts (property + asc/desc), multi-key.
- Refactor `DatabaseView.tsx` (555 lines, monolithic) into:
  - `DatabaseView.tsx` — shell: tabs + filter/sort bar + delegates to a renderer by `view.type`.
  - `views/TableView.tsx` — the existing `<table>` extracted.
  - `views/ListView.tsx`, `views/BoardView.tsx`, `views/GalleryView.tsx` — new renderers (slice 4).

**Verify (slice 3):** e2e: create a board view; set a filter `Status eq "Todo"`; GET with `?view_id` returns only matching rows; set a sort; order reflects it; switch view type. Unit test the `applyViewConfig` pure helper with `node --test`.

## Slice 4 — List / Board / Gallery renderers (frontend)

Each consumes the same `DatabaseDTO` + active `DatabaseViewDTO`.

- **ListView**: compact rows, one line each, showing the primary property (first text/title) + optionally a couple visible properties as muted chips. Click row → opens row page (slice 5).
- **BoardView**: Kanban. `group_by` must reference a `select`/`status`/`multi_select` property. Columns = the property's options. Cards = rows; drag a card between columns → PATCHes the row's cell to that option (native HTML5 DnD). Empty groups hidden by default with a "Show empty groups" toggle in view config.
- **GalleryView**: card grid (CSS grid `grid-cols-2 sm:grid-cols-3 lg:grid-cols-4`), card shows cover (first `image` block's url on the row page, if any — fetched lazily, else an icon/initials tile) + title + a few properties. Click → row page.

All three reuse the filter/sort from slice 3 (the backend already returns the filtered/sorted row set). Board's group_by is applied client-side as a partition (the rows are already filtered; grouping is presentation).

**Verify (slice 4):** Playwright UI tests: switch to Board, see columns by option, drag a card to another column changes its value; switch to List, see compact rows; switch to Gallery, see cards.

## Slice 5 — Row-as-page (backend + frontend)

Make the "rows ARE pages" fact visible and editable.

### Backend
- `GET /rows/:rowPageId` — returns the row page (reuse `getPageWithBlocks` — the row IS a page, so this may just be a route alias or the existing `GET /pages/:id` already works). Confirm and document; add a `?as=row` convenience if needed. The key addition: `getDatabase` already returns `rows[].page_id`, so the client can navigate to `/app/:ws/:rowPageId`.
- Row **title** editing: the row page's `title` becomes the "Name" property display. Wire so editing the page title updates the Name cell and vice versa. Decision: the first `text` property named "Name" (the default created by `createDatabase`) is the row's display title; `updatePropertyValue` on it also calls `page.update({ title })`, and `updatePage({title})` on a row page syncs the Name cell. Keep it to the conventionally-named "Name" property to avoid scope creep.

### Frontend
- `<tr>`/card/list-row gets `onClick` → `navigate(/app/:ws/:rowPageId)`. The existing `PageView` already renders any page (rows are pages), so opening a row shows its blocks + any nested databases automatically — no new route needed.
- `PageHeader` for a row page: add a small "← back to database" affordance and surface the row's properties as editable fields (a compact property panel above the editor), each editing via the existing `updatePropertyValue`. Reuse the `CellEditor` from DatabaseView.
- The row page's title (`contentEditable` in PageHeader) edits the Name property.

**Verify (slice 5):** e2e: click a row → navigates to a page with the row's id; edit the title → reflects in the grid's Name cell; add a paragraph block to the row page → persists.

## Slice 6 — New property types: multi_select, status, system types (backend + frontend)

### multi_select
- `options` shape becomes `{ options: Array<{ value: string; color?: string }> }` (introduce colors here; `select` upgraded to the same shape — backward-compat: read old `string[]` as `[{value}]`).
- `PropertyValue.value` for multi_select = `string[]`.
- Cell editor: a tag input with colored chips; existing options shown as pickable; new option adds to the property's option list (PATCH property options).
- Filter ops: `any_of`, `none_of`, `contains`, `is_empty`.

### status
- Same storage as `select` but `type: "status"`. UI groups options into To-do/In Progress/Done categories (the `options` config: `{ groups: Array<{name, options: string[]}> }`, with sensible defaults). This is what Board view groups on by default. Cell editor is a dropdown grouped by category.

### System types (`created_time`, `created_by`, `last_edited_time`, `last_edited_by`)
- **Read-only, computed from the row Page** — no `PropertyValue` rows stored. In `getDatabase`, after loading rows, populate these properties from `page.created_at` / `page.created_by` / `page.updated_at` / `page.last_updated_by`.
- Cell editor: read-only display (formatted date / user name). Cannot be filtered by `is_empty` (always present); sortable.
- `addProperty` for these types: no `options`, no values accepted (`updatePropertyValue` rejects with `SYSTEM_NOT_EDITABLE`, mirroring `FORMULA_NOT_EDITABLE`).

### Backend
- Extend `databases.schema.ts` type enum + options validation per type.
- `getDatabase`: add a post-processing pass to inject system-type values into each row's `values`.
- `databases.service.ts` `addProperty`: validate new types' options shapes.

### Frontend
- `CellEditor`: add `multi_select` (chip input), `status` (grouped dropdown), and a read-only branch for the 4 system types. Add the new types to the add-column `<select>`.

**Verify (slice 6):** e2e: create multi_select with colored options, set two values, filter `any_of`; create status, group board by it; created_time shows the row's creation timestamp and is read-only.

## Slice 7 — Relation + Rollup (backend + frontend) — capstone

Depends on slice 6's type framework. The "power tools."

### Relation
- `relation_database_id` (added in slice 1) points at the target db.
- `PropertyValue.value` for relation = `string[]` of target row page_ids.
- `addProperty` type `relation`: requires `relation_database_id` in `options`; validates target db is in the same workspace.
- **Two-way sync**: when a relation value is set on row A → B, the inverse property on B (auto-created or configured) reflects A. Implementation: on `updatePropertyValue` for a relation cell, also write the inverse `PropertyValue` rows (upsert) on the related rows' inverse-relation property. The inverse relation property is created lazily on the target db if it doesn't exist (Notion behavior), named `<SourceDb> (from <RelProp>)`.
- `getDatabase`: for each row, relation cells resolve to summary objects `Array<{ page_id, title }>` (the related rows' titles) for display.
- Cell editor: a searchable multi-select picker listing the target db's rows (fetched via `getDatabase` on the target).

### Rollup
- `type: "rollup"`, `rollup_config: { relation_property_id, target_property_id, aggregation: "sum"|"avg"|"min"|"max"|"count"|"show_original" }`.
- Computed in `getDatabase` (alongside formulas): for each row, read its relation values → fetch the target property's values on those rows → aggregate. Reuse the formula engine's aggregation logic where possible.
- Read-only cell; not editable. Sortable; filterable on the computed scalar.

### Frontend
- `CellEditor`: relation = picker; rollup = read-only computed display.
- Add-column form: relation type prompts for target db; rollup type prompts for (relation prop on this db) + (target prop) + (aggregation).

**Verify (slice 7):** e2e: two dbs; relation column on db1 → db2; set A relates to [B,C]; inverse appears on B and C; rollup `sum` of a target property through the relation = correct total; rollup is read-only.
